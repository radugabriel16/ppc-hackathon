# Contract / UI issues

## Live backend integration (current)

- Auth now uses the documented readable `filegrid_csrf` cookie for `X-CSRF-Token`, including after reload. The older response-header convention below is only retained for the isolated mock adapter.
- `/uploads` is DRONE_VIDEO-only and requires `DroneVideoMetadata`. The upload form now collects real destinations/timestamps; outage records and connection documents use multipart `/files`. METER_READING is not offered for user file uploads. Session states are PENDING/UPLOADING/COMPLETING/COMPLETED/ABORTED/EXPIRED, independent of file status. Negotiated chunks and destination metadata are persisted for resume.
- The backend issue GeoJSON now includes the actual optimistic-concurrency `version`. Layer properties still need explicit types in the contract; no versions are guessed. Free-text descriptions remain excluded by the backend's map privacy allowlist.
- OUTAGES may carry an asset LineString; its first network coordinate is used as the existing point-marker anchor.
- Seeded LINE_SEGMENT assets currently use Point geometry. Both Point and LineString are accepted as returned; no missing line path is invented.
- **Statistics backend unavailable:** none of the four contracted `/stats/*` routes is implemented by this backend (HTTP 404). The page surfaces errors, never mock measurements. Implementing statistics is outside this integration-only task.
- **Forecast absent:** `/stats/forecast` has no contract operation or backend implementation. The existing mock-only proposed envelope is not a production guarantee.
- **Simulator unavailable:** `/admin/simulator/*` legitimately returns 503 `SIMULATOR_UNAVAILABLE` when the service is absent. Add that response and `Retry-After` to the contract. The admin page shows the error and disables dependent controls while policies, runs and alerts remain usable.
- **Upload recovery:** status still lacks `fileId`, chunk size and expiration. Resume preserves negotiation locally and retries the backend's idempotent completion to recover `fileId`. The contract should specify completion retry semantics.
- Most response fields remain optional and statistics/GeoJSON remain opaque. The adapter validates required live fields; typed layer and statistics schemas are still needed.

The notes below record the colleague's **pre-integration assumptions**, not the current integration status. The current section supersedes conflicting statements.

## Statistics response shapes and forecast extension

The four `/stats/*` operations currently return unconstrained `additionalProperties: true` objects, with no units, dimensions, examples, query parameters or missing-value semantics. They cannot establish a production response shape. The new Statistics page calls those operations directly through the generated SDK; it no longer uses the legacy operational-count summary to populate charts. **The envelopes below are explicit proposals used by MSW and validated by `src/data/stats-mapping.ts`, not guarantees made by the current contract.** Agree these fields upstream and regenerate the SDK; only the mapping/transport layer needs changing if the agreed wire format differs.

- `GET /stats/storage-benchmark`: `{rows: StorageBenchmark[]}`. A row contains `category` (the four file categories), `storage` (`db|ftp|s3`), `profile` (`normal|peak`), `p50Ms`, `p95Ms`, `p99Ms`, `throughputMiBps`, and `errorRate` (fraction in `[0,1]`, displayed as percent). Durations are milliseconds, throughput is mebibytes per second. Numbers must be finite/nonnegative, percentile order must be valid, and category/storage/profile combinations must be unique. The profile toggle filters returned rows locally; no undocumented query parameter is sent. Missing matrix cells say “No data yet”; they are never zero-filled. The heatmap metric is independently selectable; the table always shows all five metrics.
- `GET /stats/recommendations`: `{items: [{category, storage, reason}]}`. At most one recommendation per category; the reason must come from the response. Missing categories have no synthetic recommendation. This endpoint is global rather than region- or profile-specific because the contract defines no filters.
- `GET /stats/meters`: `{meters: [{id, label, regionCode, intervalMinutes, from, to, readings: [{timestamp, kWh, anomaly}]}]}`. `regionCode` is one of the three known codes. `kWh` is interval energy, not a cumulative register or power measurement. `anomaly` is `spike|zero|gap|null`; missing/null anomaly means unflagged. `from/to` are inclusive expected sampling bounds; all timestamps require an explicit offset. Values are nonnegative or `null` for missing readings. Within an aligned, nonempty reported window, omitted timestamps become **null gaps**, including leading/trailing gaps; no consumption is imputed. Completely empty reading arrays remain empty. Duplicate/misaligned timestamps, invalid windows, or more than 10,000 intervals fail explicitly. Zero is preserved as a measured value. Region and meter selection are local filters; the backend must define query/window/pagination support before production-scale histories are used. Operational meter labels contain no customer personal information.
- `GET /stats/outages/hotspots`: a GeoJSON `FeatureCollection` of Points with `[lon, lat]` and properties `{id, assetName, regionCode, outageCount, durationMinutes}`. Count is a nonnegative integer; duration is nonnegative total outage minutes. Coordinate and property validation is strict; the map forwards only operational asset/count/duration fields. Heat uses outage count as its weight; cluster labels sum outage counts, rather than counting feature markers. The table shows the same returned values, sorted by count, and remains usable without WebGL. The contract must also define the aggregation window and asset-vs-region granularity; the UI does not assume a period or invent coordinates from asset IDs.

**`GET /stats/forecast` is absent from `contracts/openapi.yaml`.** It is an explicit mock extension, with this proposed response (all point values are interval kWh):

```json
{
  "series": [
    {
      "regionCode": "MUNTENIA",
      "unit": "kWh",
      "points": [
        {
          "timestamp": "2026-11-14T12:15:00Z",
          "estimate": 200000,
          "lower80": 184000,
          "upper80": 216000,
          "lower95": 173000,
          "upper95": 227000
        }
      ]
    }
  ]
}
```

There is at most one forecast series per region. Points must have unique timestamps, finite/nonnegative values and nested bounds `lower95 <= lower80 <= estimate <= upper80 <= upper95`. The UI sorts timestamps and draws the returned bounds as shaded 80%/95% intervals. It never computes a forecast or uncertainty bounds from live observations. Model provenance, horizon/cadence, training cutoff, interval calibration and server filtering are not defined; the mock is a synthetic visualization example, not an operational prediction.

Until the forecast operation is added upstream, `ApiSource.getForecast` calls `/stats/forecast` using the **same generated fetch client's transport**, including the configured base URL, cookie credentials and normal error handling. Generated files and the read-only contract are untouched. When the operation exists, replace this one transport call with its generated SDK operation. A live 404/501/network failure remains a visible error with the available request ID; there is no mock fallback.

For all five endpoints, an empty object, empty collection envelope, null/empty response or empty array maps to **“No data yet”**. Nonempty unknown shapes or invalid measurements produce `CONTRACT_MISMATCH` instead of plausible-looking values. A region with no records is empty. API mode never imports statistics fixtures or synthesizes measurements, recommendations, coordinates or bands. The existing unused `getStatistics`/`useStatistics` operational summary remains available for compatibility and is not used by this page.

MSW supplies deterministic synthetic telemetry only in explicitly selected mock mode: all 24 category/storage/profile cells, four recommendation narratives, three meters per region with daily variation/spike/zero/omitted and explicit-null readings, 18 hotspot assets per region, and 48 forecast intervals per region with widening nested bands. Every statistics mock GET, including forecast, requires a session and accepts either role. LocalDemoSource returns empty collections for these new measurements because its existing file/issue records contain no benchmarks, consumption or forecasts.

## Admin integration

- `SimulatorBackfillRequest` contains only `profile`, `from`, and `to`; there is no `anomalies` field or enum. The UI sends the selected **spike / zero / gap as `profile`**, with ISO date-time bounds converted from local input. Confirm these profile names and their anomaly semantics with the backend; no undocumented request property is sent. Start profiles **normal / peak / storm** and a positive finite readings rate are UI/mock validation rules; the schema currently leaves profiles and numeric ranges unrestricted.
- Policies, simulator state, scenario runs and alerts have no supplied examples. MSW supplemental records use the generated contract types. Policy reload returns the mock configuration; simulator controls persist state and run records in IndexedDB, but do not generate readings or execute real workloads. Mock backfills complete immediately and add a sample anomaly alert. This does not require or expose a simulator bearer token in the frontend.
- All `/admin/*` mock routes enforce MANAGER access, and POST routes enforce CSRF. `/alerts/recent` specifies authentication only, so the mock permits either authenticated role, while its Admin-page UI remains MANAGER-only. Confirm any intended server-side role restriction on that endpoint.
- Optional policy values display as unknown rather than invented defaults. A missing simulator `running`, scenario ID, alert ID/message, or page envelope field fails explicitly. The contract has no scenario-run status/progress/error field and does not distinguish an omitted `endedAt` from an active run; the table displays returned timestamps and counters without inventing a completion status. Scenario pagination is sent to the server; no ordering query is defined, so returned order is preserved.
- Status, runs and recent alerts refresh every 10 seconds while the page is active. All Admin POSTs use the generated SDK and the same provisional CSRF delivery noted above; live mutations remain blocked if the backend does not supply the token.

## Mock scope and limits

Both `mock` and `api` use **the same ApiSource and generated SDK**. MSW intercepts HTTP only in explicitly selected mock mode. Unhandled `/api/v1/*` operations return an explicit 501; map tiles and Vite assets are passed through. API mode never imports/starts the browser mock module and deactivates/unregisters a leftover MSW worker when switching modes. Worker startup failures are shown, without falling back to live or demo data.

The mock serves supplied examples as the source for assets, map features, file metadata, checklists and upload chunk negotiation. Region/session/case-list/document-reference/verification envelopes are explicit supplemental mock records because these examples were not provided. Upload negotiation regenerates IDs, totalParts from the selected file size, and future expiry; the fixed example's January 2026 expiry is already past. Upload parts and sessions persist in IndexedDB through the existing fake server, with checksum checks, retries and dropped acknowledgements. Auth/session mock state also persists in that demo store; it is not production cookie security. New mock issues are persisted, versioned, and manager resolution is enforced.

Resume records are namespaced by data mode, API URL, and username. Prior LocalDemoSource upload IDs are never resumed against the API. `LocalDemoSource` remains available for isolated demos/tests, but is not an automatic mode or fallback.
