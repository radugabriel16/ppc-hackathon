# Worker operations

## Operational issues and geographical forecasts

`0006_operational_forecasts` marks **all pre-existing map issues** historical,
without deleting issues, linked entities or observations. It is forward-only:
removing the epoch flag would expose the old issues again. List/map/issue-count
views and issue reminders exclude historical issues; `includeHistorical=true`
on the read APIs requires MANAGER. New issues are operational.

In the new APIs, **segment = subregion**: three regions, six subregions each.
The model's segment is just an aggregation key for per-meter predictions.
The adapter supplies `meters.subregion_id`, subregion code and parent region
to `History.from_frames`, with all eight registered meters per subregion
(`expected_meters=8`). No retraining or double-summing is involved. Legacy
`GET /segments/{id}/forecast`, `/meters/{id}/forecast` and `/stats/forecast`
retain their original network-asset grouping for compatibility; new consumers
should use `/forecast/runs`. The consumption model does not read outage/issues
history, per the handoff; retaining that history does not change its inputs.

`POST /api/v1/forecast/runs` accepts `{"scope":"country"}`,
`{"scope":"region","regionId":"..."}`, or
`{"scope":"segment","segmentId":"...","regionId":"..."}` (region optional).
The sync handler runs inference/SQL in FastAPI's threadpool and returns a
completed, persisted run, its segment forecasts and newly created issues.
`GET /forecast/runs/{id}` reads that snapshot without recalculation.
Failures are persisted as FAILED; the error response's `Location` header links
to the failed run. A process killed during inference can leave RUNNING; no
automatic retry is claimed. Country runs can take longer than a gateway timeout;
they are not a durable asynchronous queue.

The three target dates are **tomorrow, +2 and +3 UTC calendar days**, never
relabeled predictions from a different origin. `asOf` is bounded by the actual
query time: future/late observations are not fabricated. For tomorrow-origin
runs only, missing six-hour slots of **today** are bridged with the per-meter
median of the matching slot on the previous four same weekdays, requiring at
least two available samples. Actual arrived slots are unchanged. This private
inference history then feeds the unchanged three-day model; estimates are never
written as readings. Segment, meter and day `bridged` flags and the segment's
`bridge` metadata expose the method, day, slot count and real `asOf`.
Last-completed-day metadata still excludes today. Historical gaps are not
bridged; genuinely insufficient model history uses the explicitly flagged
recent-daily-mean baseline (`fallbackReason=INSUFFICIENT_HISTORY`), or
null/INSUFFICIENT_DATA when no daily observations exist, never zero.
Untyped meters use all-zero client-type indicators, with `clientTypeUnknown`
and `unknownClientTypeMeters` disclosed; no client metadata is inferred or changed.

`GET /forecast/thresholds` and MANAGER-only
`PUT /forecast/thresholds/{segmentId}` (`{"dailyEnergyKwh":400}`) manage positive
finite limits. Defaults are calibrated from **p95 of complete daily segment
totals over the previous 28 UTC days, times 1.03**, with at least 14 complete
days required (otherwise explicit 503). The 3% demo headroom yields a small
number of genuine model exceedances rather than the old blanket 400 kWh limit;
it is not a guaranteed issue quota or a production capacity recommendation.
Invalid/incomplete/unavailable slots exclude their whole segment day. Calibration
never uses bridged or forecast values. The seeder calibrates defaults, and runs
refresh defaults once per UTC day. `source`/`calibration` on thresholds and
`thresholdSource`/`thresholdCalibration` on run segments record provenance.
Manager updates set MANUAL and survive reseeding/recalibration.
Migration `0007_forecast_calibration` preserves previously audited overrides
(and non-400 values). These are daily energy limits, not physical kW capacity.
A database unique index deduplicates ML_FORECAST
issues by segment/date, including concurrent reruns; the same transaction writes
the issue and existing `alerts` row. Reruns retain the original issue/alert
snapshot and store their new calculation in the new run.
Issue/alert titles state "<segment> expected to exceed on <date> by X kWh".

`POST /map-issues` accepts OUTAGE_REPORT (default), OUTAGE_VIDEO and
DRONE_DETECTED. Video types require a READY uploaded DRONE_VIDEO file (the existing
video storage category); a video inspection must match the asset and file.
Uploading footage alone does not assert a defect: the caller reports a detected
point using this API. ML_FORECAST and MISSING_DOCUMENTS cannot be manually forged.
Titles/descriptions are generated by type, with optional operator details.
The supplied point is stored unchanged in EPSG:4326; `ST_Covers` determines its
region/subregion. Points outside Romania, the operational areas, or an asserted
region/segment return 422. Shared-boundary ties use the first covering subregion
by code, as the existing database trigger does.

`GET /map-issues` filters by type, status, regionId, segmentId/subregionId,
clientId, and inclusive `from` / exclusive `to` creation timestamps.
`GET /connection-cases` supports the same geographic/client/date filters,
case status, and a linked operational issue type; its date field is openedAt.
`GET /clients/missing-documents` paginates clients with incomplete required
READY-document checklists, filterable by region/segment and optional case status.
Closed cases are included unless filtered: closing a case does not manufacture
the required documents. The worker synchronizes one MISSING_DOCUMENTS issue per
incomplete case, resolves it on completion, and reopens it if the checklist regresses.
Client geography uses its real point, otherwise an in-region linked meter,
otherwise the parent region's representative point, explicitly synthetic.
No client name/email is exposed by these map features.

`ROLE=worker` reuses the five-second upload loop. PostgreSQL session advisory
locks serialize each job across replicas without holding SQL transactions during
storage or SMTP calls. `worker_state` persists scheduling and scan cursors.
`WORKER_BATCH_SIZE` defaults to 25; upload recovery retains its existing
100-session bound per operation. The existing loop schedules at most one local
task per job; a slow scrub does not block reminders, gap sampling or upload
recovery. Shutdown cancels and joins all local job tasks.

READY files are scrubbed every `INTEGRITY_SCRUB_INTERVAL_SECONDS` (86400).
Reads use the existing decrypt/hash/storage instrumentation and bulkheads.
`INTEGRITY_SCRUB_BYTES_PER_SECOND` (5242880) paces whole-file reads, averaged
over transfer plus post-read sleep, rather than slowing an individual transfer
past its storage deadline. A run reads at most one batch; large files can
therefore delay that job's next run. Storage failures are deferred by
`WORKER_RETRY_SECONDS` (300), not treated as corruption.

After `STUCK_FILE_AFTER_SECONDS` (3600), abandoned direct STAGING files become
FAILED (`STAGING_ABANDONED_METADATA_UNAVAILABLE`): their original linking metadata
cannot safely be reconstructed. Active multipart sessions are left to the
existing completion/expiry recovery. Unlinked VERIFYING files fail explicitly;
linked ones retry full verification, at most `WORKER_MAX_ATTEMPTS` (3), before
`VERIFY_RETRIES_EXHAUSTED`. Failure reasons and cleanup progress are durable.
Failed writes are deleted on their recorded backend and possible policy fallback.
All three storage inventories are scanned with durable UUID cursors, one batch
per backend per iteration; objects older than ten minutes without a catalog
reference on that backend are deleted. STAGING files protect possible fallback
writes. FTP lacks server pagination, so its MLSD scan streams into bounded
memory under an explicit deadline; deletion remains batch-bounded.

## Meter missing-reading rule

`filegrid_meter_readings_missing{region}` is a shared snapshot of **observed
internal gaps**, not a prediction of future readings. A meter is active only if
both its most recent received reading and latest interval end are within
`METER_ACTIVE_SECONDS` (300) of now. Old backfill does not reactivate it.
Never-seen and idle meters contribute zero even when no simulator is running;
there is no trailing-gap extrapolation after the last observed interval.

For each active meter, compare consecutive readings ordered by interval end,
inside `METER_GAP_WINDOW_SECONDS` (3600), bounded to the newest
`METER_GAP_READINGS_LIMIT` (1000) readings. Add the larger of the sequence gap
and interval gap (rounded up using the preceding interval duration), avoiding
double-counting the same loss. Sequence resets do not themselves create gaps.
The meter scan resumes by UUID each batch; snapshots expire at the activity
deadline even on non-owning worker replicas. Each known region exports zero
when no active gaps remain. Region codes, never meter IDs, are labels.

## Reminders

PHASE1 defines no reminder cases, so the worker reminds the operations mailbox
about unresolved issues older than `REMINDER_AFTER_HOURS` (24), and OPEN
connection cases missing any required READY document. Closed cases, resolved
issues and complete checklists do not qualify. SMTP uses `SMTP_HOST=mailpit`,
`SMTP_PORT=1025`, `REMINDER_FROM=filegrid@filegrid.local` and
`REMINDER_TO=operations@filegrid.local`; provision the SMTP service separately.
Messages contain entity references, not client names, addresses or documents.

`REMINDER_PERIOD_HOURS` (24) defines UTC epoch-aligned periods. The dedupe key is
(kind, entity, period). An attempt is committed **before** SMTP: retries and
replicas never duplicate a period's mail, including ambiguous SMTP acknowledgments.
SMTP cannot participate in a database transaction; a crash after reservation or
failed send may lose that period's email. ATTEMPTED/FAILED rows expose this
at-most-once tradeoff, failures are logged, and the next period is eligible again.

## Telemetry

`filegrid_document_access_total{action,outcome}` accompanies the existing audited
document download path. `requested` counts the committed audit entry; `success`
means the complete plaintext passed verification; `failure` includes integrity,
storage and cancelled reads. No separate document-view endpoint currently exists;
the reserved `view` series stays zero. Do not sum requested and success as if they
were separate accesses.

Tracing is disabled unless `OTEL_EXPORTER_OTLP_ENDPOINT` or
`OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` is set. Standard OTEL resource, sampler,
headers, timeout and TLS exporter settings apply; protocols are `grpc` (default)
and `http/protobuf`. `OTEL_SDK_DISABLED=true` or `OTEL_TRACES_EXPORTER=none`
disables initialization. The default service name is `filegrid-<role>`.
FastAPI, httpx, SQLAlchemy and asyncpg are instrumented; health/metrics requests
are excluded. Each worker job run has a span, and JSON logs include `trace_id`
(null without an active trace).

Run the integration suite with `bash scripts/test_storage.sh`. It temporarily
pauses a running worker so background jobs cannot consume the tests' deliberate
stale files/reminder candidates, and restores it (and FTP) even if tests fail.
